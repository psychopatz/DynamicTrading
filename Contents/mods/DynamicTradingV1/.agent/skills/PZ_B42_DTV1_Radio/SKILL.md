# Dynamic Trading V1 (Radio Module) Architecture

The Dynamic Trading V1 module acts as a **legacy radio interface and discovery layer** that sits on top of the `DynamicTradingCommon` core. It DOES NOT manage the actual economy, item generation, or physical NPC placement.

## Core Rules

1. **V1 is a Presentation Layer**: V1 only handles the Radio UI (`DT_RadioWindow`, `DT_TraderListPanel`, `DT_SignalPanel`) and the mechanics of scanning frequencies to discover contacts.
2. **Delegation to Common**: All heavy lifting (Stock Generation, Trade Transactions, Roster Management, Faction Wealth) is strictly handled by `DynamicTrading_Engine`, `DynamicTrading_Roster`, and `DynamicTrading_Stock` in the Common module.
3. **No Direct Spawning**: V1 never physicalizes NPCs into the world. It deals entirely in radio signals (UUID references to souls in the Roster).
4. **The Discovery Bridge**: When a player scans the radio, they are discovering existing `Souls` in the Common Roster that have their `status` set to "Trading".
5. **Shared Expiration Logic**:
   - When a generic soul is discovered via the radio for the FIRST time, V1 creates a "Discovery Bridge" entry in `data.RadioTraders`.
   - This bridge entry assigns a `returnTime` (expiration) using the sandbox settings `TraderStayHoursMin` and `TraderStayHoursMax`.
   - Because `data.RadioTraders` is synchronized across all players, **discovery and expiration are shared globally**. If Player A discovers a signal, and Player B later discovers the exact same signal, they share the same expiration timer generated by Player A.

## Key Functions

- `DynamicTrading.Manager.DiscoverTrader(traderID, player)`: The critical bridging function. It takes a `traderID` from the shared roster, checks if it exists in the V1 radio data, and if not, creates the V1 metadata (including the shared expiration timer) and adds the player to the `discoveredBy` list.
- `DynamicTrading.ServerCommands.AttemptScan`: The server-side RNG roll that triggers `DiscoverTrader` when successfully scanning a frequency.
- `DynamicTrading.Manager.GetTrader(traderID, archetype)`: Builds a V1-compatible object by combining the Common `Soul` data, Common `Stock` data, Common `Faction` data, and V1 `Radio` metadata.

## Best Practices

- **Do not bypass the UI**: Always check `CheckConnectionValidity()` to ensure the radio is powered and nearby.
- **Do not duplicate counting logic**: When determining how many signals a player has found, use `DynamicTrading.Manager.GetDiscoveredCount(player)` which correctly checks local expiration limits and generic roster soul states.
- **Null Safety**: Always verify that the underlying `Soul` still exists in the Roster when dealing with V1 Radio trader objects. If the soul is missing, the trader is treated as invalid and filtered out of the UI.
